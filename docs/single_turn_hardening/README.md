# 单次 Prompt 修复与 schema 8 升级（2026-09-23）

版本：Bumi_Mem 0.5.1 / HTTP API 1.3.1。**不改用户约定的六个输入字段、不增加调用次数，正常响应仍只有 turn_id 和 prompt。**

## 修复范围

1. 核心保存失败通过长期区的一句事实性说明传达，仍保留可读的已有核心规则。
2. 自动整理的来源时间数组保留到Prompt；多来源只说明抽取输入范围，不推断单条事实的发生时刻。时间排序按带偏移的真实瞬间，不按ISO字符串字面顺序。
3. 控制记录使用真实执行结果，区分失败、取消、未开始、结果未知与已停止。反馈音状态不能代替执行结果。
4. 新旧幂等记录明确区分协议，并用旧接口不可能接受的内部表示隔离键；缓存格式不符返回409，不再返回错格式的200。
5. 恢复有界引用选择（默认6,000字符）和16条历史版本。按最新可容纳记录优先，不在半句话截断。时间/状态不同的记忆不会仅因正文相同而合并；裁剪不会伪装成没有记忆。当前核心不因检索预算被丢弃。
6. 数据中的换行、章节标记、身份中的方括号及不可打印字符在展示时转义。每条原始发言仍保持一条记录、数据库原文不变；这不是通用LLM提示注入免疫机制。

## 输出与使用

短期普通中文原话仍直接可读；含换行/特殊标记的内容以JSON字符串转义形式显示。例如用户正文中的真实换行显示为字面的 `\n`，数据里的 `[` 显示为字面的 `\u005b`。服务自己的 `[长期记忆]`、`[短期对话]` 和逐条时间标头不受影响。

Agent只需要正常解析HTTP JSON并使用prompt，不要再进行二次转义展开，也不要把prompt当作身份授权协议重新解析。现有Agent人设、工具规则和真实执行结果仍由Agent持有。

引用预算只约束检索引用的展示，短期仍按现有L1预算选择；它不是完整LLM请求的总token/延迟承诺。

## 为什么需要 schema 8

v7把新单次ID存为可打印的 `turn:<id>`，但旧接口也允许完全相同的Idempotency-Key；而部分旧记录完成后会清掉缓存，从而丢失判断模式的证据。

v8只修改HTTP请求元数据：

- 为context_requests增加request_kind与pre_v8_key，记录缓存模式与迁移前编号；
- 新内部键无法通过旧接口的可打印ID校验；
- 能根据缓存识别的新单次记录迁移到独立空间，旧编号仍保留，防止另一模式把它当作全新输入；
- 丢失格式证据的旧记录保留，不推测归属、不自动重放；复用时返回 `409 request_protocol_ambiguous`；
- 旧模式/损坏缓存混用返回 `409 request_protocol_conflict`；
- 涉及旧单次/无法辨识记录的agent缓存版本递增，避免继续重放修复前错误Prompt。

**没有重写原消息、个人核心版本或向量库，没有凭旧对话自动补写曾失败的核心变更。** 升级前已发生的错误确认也不能倒退撤销。

现有同一模式重试仍幂等；新库里合法旧header `turn:t1` 与新body `turn_id=t1` 可以独立使用，不会跨模式返回缓存。迁移前有同名记录的情况更保守，宁可明确冲突也不猜测重播。

## 升级步骤

1. 暂停Agent新输入；结算正在进行的语音/工具与未确认请求，尤其不要在升级时继续消费旧Prompt缓存。
2. 停止旧记忆服务；对数据目录做一致备份，包含SQLite及必要WAL状态和对应L3存储。不要只复制正在写入的单个.db文件。
3. 先在备份副本上使用新版启动并验证迁移。保留原user_id/agent_id，不能用改归属后全空查询来判定迁移成功。
4. 启动新版后，旧Prompt重试可能得到 `shared_memory_context_changed`；这是主动使旧快照失效，不是丢失原发言。已确认的旧回复仍可按原单次顺序补存，然后开始新轮。
5. `request_protocol_ambiguous` 需要对照升级前的Agent/outbox记录核验；禁止换一个ID来自动重放旧问题或把未知回复随意挂给当前轮。
6. 只有确认旧任务、播放状态和请求归属之后才恢复发送。若不能确认，停止该记录的自动推进并交由运维处理，不手工改SQL字段猜归属。
7. 回滚需要恢复升级前备份。旧二进制拒绝schema 8，不能仅修改PRAGMA user_version“降级”。

当前本地修改与测试没有打开真实服务器数据库。生产升级由用户择时执行。

## 验证范围

新增离线回归覆盖：保存失败、真实整理元数据的时间来源、跨时区范围、控制失败/未知、可逆转义、预算、时间不同的同文记忆、协议前缀碰撞、错误缓存、旧库迁移、重启与冲突保护。所有测试使用临时SQLite/Fake Provider，不调用真实DeepSeek或硬件。

格式边界保护不等于语义安全证明；真实模型回答质量、已有机器人数据、网络与GPU性能仍需单独验收。
